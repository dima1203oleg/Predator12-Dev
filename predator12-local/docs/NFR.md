# Нефункціональні вимоги (NFR) — GitOps / Helm / CI

Цей документ описує нефункціональні вимоги для автономного Helm GitOps pipeline, CI workflow-ів та пов'язаних скриптів у репозиторії.

1. Надійність і стабільність

- Скрипти мають бути ідемпотентними: повторний запуск не повинен призводити до нефіксованих змін у віддаленому репозиторії або кластері.
- Dry-run режим (DRY_RUN) повинен існувати у кожному скрипті, який може впливати на віддалені ресурси. За замовчуванням pipeline повинен виконувати dry-run, доки ручне підтвердження не змінить режим.

2. Резилієнтність CI

- Пайплайни повинні виживати у випадку shallow checkout / sparse-checkout (виконувати defensive checkout: fetch-depth:0, --unshallow, git submodule update --init).
- Pre-job/post-checkout hooks не повинні падати якщо очікувані файли відсутні — забезпечити non-blocking shims або додати мінімальний placeholder у дефолтну гілку.

3. Безпека й права доступу

- Усі push-операції повинні виконуватись з використанням обмеженого токена з мінімальними правами; секрети не повинні потрапляти у логи.
- CI, що має змогу мерджити/пушити (autodeploy), повинен проходити додаткову перевірку політик (Cosign, image scan, policy checks).

4. Спостережуваність і аудит

- Кожен автодеплой повинен логувати: headSha, branch, змінені файли, результати helm lint, результати dry-run, і результат push (success/fail).
- Звіти та артефакти (rendered manifests, logs) повинні бути завантажені як artifacts після виконання job.

5. Відкат і atomicity

- Пуші, які змінюють gitOps manifests мають бути atomic (single commit) і мати можливість rollback (створювати PR або тег з попереднім станом перед застосуванням).

6. Продуктивність

- Timeout для конкуренційних моделей/завдань CI має бути налаштований; великі операції (render, helm template) повинні мати зрозумілі таймаути та повтори.

7. Тестування та валідація

- Додати unit-тести для ключових bash/python scripts (happy path + error path).
- CI має мати швидкі smoke-тести (pytest) перед виконанням довгих job-ів.

8. Документація і процеси

- Описати процедуру emergency rollback у `docs/`.
- Вказати процес релізу: створення branch `auto/autodeploy-tz`, правила мерджу/approval для автодеплойних PR.

9. Сумісність і portability

- Скрипти мають працювати на VM Ubuntu (runner) та локально (macOS zsh). Використовувати POSIX-совісний bash та перевіряти залежності в README.

10. Observability metrics

- Експортувати метрики (duration, success_rate) у Prometheus/Grafana для важливих job-ів.
